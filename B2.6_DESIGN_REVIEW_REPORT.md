### Interaction Flow Findings

**Approved flow (static reference):** View vehicle → see non-profit notice → contact provider via WhatsApp/phone (no request creation in the reference)

**Current flow (implemented):** View vehicle → select services → obtain fresh GPS → create tracked request (POST `/api/mobile/v1/requests`) → backend confirms → external handoff (WhatsApp/dialer). **The current screen implements the full B2.5B–F tracked request workflow**, which is a **superseding requirement** over the original static UI reference.

**Order of operations (current, verified):**
1. Validate screen state (vehicle loaded, not loading/error)
2. User selects services (chips toggle selection)
3. User taps "Send request" CTA
4. **If channel = 'app':** POST immediately, show success/failure feedback, no handoff
5. **If channel = 'whatsapp' / 'phone':** 
   a. Validate driver has usable phone number
   b. Request fresh location (GPS permission → timeout → unavailable handling)
   b. If location valid: POST `/api/mobile/v1/requests` with coords + channel + services
   b. If location invalid: show error, keep services selected, no POST
   c. Backend confirms creation (HTTP 200, request object returned)
   d. Set `pendingHandoffRef`, prepare handoff data (request + phone + whatsAppMessage)
   e. Open external app: `whatsapp://send?phone=...` or `tel:...`
   f. Handoff outcome: 'opened' → success feedback; 'failed'/'deferred' → info feedback
6. Persistent bottom bar remains active; retry handoff available if user returns

**GPS permission/timeout handling:**
- `denied` → "Location permission is required to create a request. Tap the button to allow it and try again."
- `timed-out` → "Your current location could not be determined in time. Move somewhere with a clearer signal and try again."
- `unavailable` → "${result.error ?? 'Your current location is unavailable.'} Try again to send the request."
- (0, 0) always rejected at D2 contract level: "Your current location could not be used for this request. Move to an open area and try again."

**Error clarity (all three channels):**
- 409 conflict → "This request conflicts with an earlier attempt (HTTP 409): ... Nothing was resubmitted"
- 422 validation → "The server rejected these request details (HTTP 422): ... Your services are still selected."
- network error → "The request could not reach the server (network error). Your services are still selected — retry when the connection is stable."
- missing services → "Select at least one service before sending a request."
- missing phone (whatsApp/phone) → "This provider has no usable WhatsApp number / phone number"

## F. INTERACTION FLOW FINDINGS

### Request Creation Flow (three channels)

**1. App channel:**
- User selects services → taps "Send request"
- POST `/api/mobile/v1/requests` with `{vehicleId, driverId, services, channel: 'app', latitude, longitude}`
- Backend confirms (200) → shows `Request #id created. The provider will contact you.`
- No external handoff; request is standalone
- **Advantage:** fastest path; no app switching

**2. WhatsApp channel:**
- User selects services → taps "Send request (WhatsApp)"
- Validate driver has usable WhatsApp phone number
- Request fresh location (GPS permission flow)
- If location valid: POST with coords + `channel: 'whatsapp'` + services
- Backend confirms (200, request object)
- Prepare handoff: `{channel, request, phone, whatsAppMessage}`
- Set `pendingHandoffRef`, show "Request saved. WhatsApp was opened — send the message..."
- Open `whatsapp://send?phone=...&text=...` (or web fallback `wa.me/...`)
- Handoff outcome 'opened' → success feedback with "send the message to reach the provider"
- Handoff outcome 'failed' → error feedback "WhatsApp could not be opened"
- Handoff outcome 'deferred' → info feedback "was not opened because the screen lost focus"

**3. Phone channel:**
- Identical structure to WhatsApp but `tel:${prepared.phone.dial}`
- Handoff outcome 'opened' → success feedback "The phone dialer was opened — place the call to reach the provider"

### Concurrency & Idempotency
- `operationRef` monotonic counter: each vehicle change or unmount increments it; late continuations for old vehicles are invalidated
- `busyRef` ref admission control: second press during busy state is ignored (React hasn't re-rendered yet)
- `logicalRequestIdentity(vId, driverId, sortedSvcIds, channel)` — identity excludes coordinates; same identity reuses pending key, different identity starts new attempt
- `explicitNewIntentRef`: set when user changes selection after a shown success → starts new logical request
- 409 handling: `retryIdentityRef.current = outcome.error.status === 409 ? null : identity` — on 409, the pending attempt is invalidated; on other failures, the same identity resumes
- **No duplicate POSTs:** idempotency key + fingerprint; same key + different payload → 409; different key → new request

### GPS/Location Flow
- `useUserLocation()` from `UserLocationProvider` (React Context, app scope, memory-only)
- `requestLocation()` → Expo `PermissionsAndroid.request(ACCESS_FINE_LOCATION)` (Android) or `requestAuthorization()` (iOS)
- `LOCATION_GRACE_PERIOD_MS = 10_000` (10s foreground balanced accuracy)
- `Promise.race`: timeout wins; still-pending position result is **ignored entirely** (never applied to state)
- If position promise does not settle within window → `status: 'timed-out'` (explicitly NOT a permission denial)
- Fresh location result structure: `{ ok: true, coords: { latitude, longitude } }` or `{ ok: false, status: 'denied' | 'timed-out' | 'unavailable', error?: string }`
- `isUsableRequestCoords()` rejects (0, 0), out-of-range, non-finite; accepts individual valid zeros

### Channel‑Specific Flows
| Step | App | WhatsApp | Phone |
|---|---|---|---|
| Validate services selected | ✅ | ✅ | ✅ |
| Validate driver phone | N/A ✅ | ❌ if null → error | ❌ if null → error |
| Request fresh location | ✅ | ✅ | ✅ |
| POST to `/api/mobile/v1/requests` | ✅ | ✅ (after location) | ✅ (after location) |
| Backend confirms creation | ✅ | ✅ | ✅ |
| Open external app | N/A | `whatsapp://send` | `tel:` |
| Success feedback | "Request #id created..." | "Request #id saved. WhatsApp was opened..." | "Request #id saved. The phone dialer was opened..." |
| Failure feedback | descriptive error | descriptive error | descriptive error |

### State Preservation Across Navigation
- `vehicleId` change → `useEffect` resets all screen-local state (`setBusy(false)`, `setStage(null)`, `setFeedback(null)`, `setSelectedServiceIds(new Set())`, `resetCreateRequest()`)
- `pendingHandoffRef` is **not** carried over vehicle change: `pendingHandoffRef.current = null` in the `vehicleId` effect
- `retryIdentityRef` is keyed by full `logicalRequestIdentity` → survives navigation while same vehicle/channel/services; different vehicle cannot reuse it
- `presentedCompletionRef` tracks which vehicle's success was shown; new vehicle clears it via `explicitNewIntentRef`
- `focusedRef` tracks whether screen is currently focused; handoff from background is blocked if `!focusedRef.current`
